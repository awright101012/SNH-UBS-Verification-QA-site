Engineering deep dive

The AI investigates and decides. The harness checks the evidence, limits the change, and confirms the result.

The engineering problem is not making a model sound certain. It is letting the AI investigate a messy case, return an exact decision, and independently checking that decision before the machine changes anything.

A QA answer is useful only when the operation can act on it.

A free-form explanation is not a QA decision. It does not say which field may change, what value the system expects to find, which evidence supports the replacement, or what must happen after the edit. It also cannot protect itself from stale data, a duplicate instruction, or a write that only partly succeeds.

The worker separates judgment from execution. The AI interprets the evidence and makes the QA decision. Plain code checks whether the exact change is supported and allowed before anything can be written.

The separation matters because each side is strong where the other is weak. The AI can connect context that ordinary rules cannot. Plain code can enforce boundaries that must never drift.

The full case record is the first control.

The model never begins from a warehouse row or a reviewer’s final answer. The worker assembles one current case containing only the facts needed to decide and execute QA: supplied and verified values, evidence, where the case stands, rules, and the actions permitted for that product.

Historical reviewer outcomes may be used in offline evaluation, but they do not enter the live prompt. That prevents the model from copying the answer it is supposed to produce.

The remaining coverage gap is now concrete: cases without sufficient structured evidence need a richer case package or an approved lookup before the AI can decide them.

Take the right workOnly supported case types enter

Record the version being evaluated. Unsupported work remains in its ordinary source workflow.

02

Build the case recordFacts, evidence, rules, and available actions

Gather the current information and the exact handbook rules that apply.

03

InvestigateApproved missing facts for this case only

Let the AI retrieve a missing decision fact without exposing another case or an open-ended search.

04

DecideApprove or name the exact supported change

Require one structured decision with citations, rationale, and the full change when an edit is proposed.

05

CheckEvidence, current value, and allowed action

Verify that the rule applies, the evidence belongs to this case, the source is current, and the proposed value follows from the record.

06

ExecuteApply the verified decision once

Write only the checked decision, using the expected current value to prevent an overwrite if the case changed underneath the AI.

07

Read backConfirm what actually changed

Read the case again, compare the actual result with the approved decision, and record what happened.

The model may investigate, but it cannot expand its own job.

A tool request names the missing fact, the reason it matters, and the current case. The tool either returns a case-bound fact with a receipt or refuses. The model cannot invent a new tool, request a write, broaden the case, or turn lookup exhaustion into approval.

The investigation budget expands only while a permitted lookup is producing decision-relevant evidence. If approved lookups still cannot establish the answer, the worker makes no decision and writes nothing.

The verifier does not decide the case a second time.

The AI handles equivalence, context, and interacting rules. The verifier handles hard truths that software can establish without interpretation. It asks whether the AI’s decision is coherent, supported, current, and within the worker’s allowed actions.

Evidence

Does every cited fact exist in this case?

Invented receipts, cross-case references, and unsupported replacements stop the action.

Rules

Does the handbook basis exist and apply?

The AI cannot cite a rule that is absent, inactive, or outside the case’s product scope.

Freshness

Is the source still the version the AI read?

An expected current value prevents the worker from overwriting a newer human or machine change.

Allowed change

May this field and QA action be changed here?

The worker can use only approved fields, value forms, and QA actions.

Isolation

Did every lookup and receipt stay inside one case?

Case identity travels through the full investigation and verification chain.

Safety

Would the write introduce forbidden or unsafe content?

Unapproved free text and sensitive material cannot cross the write boundary.

Execution has two valid outcomes: confirmed action or zero writes.

A verified decision is previewed against the current case, applied once, and read back. The execution record includes the before value, intended change, system response, and actual final state. Repeating the same instruction does not apply the change again.

Confirmed action

Readback matches the decision.

The case is approved or changed, the required QA action is finished, and the audit history preserves what was proposed, checked, written, and read back.

Zero writes

Independent checks cannot verify a supported action.

The case remains unchanged. Unrelated cases continue. A repaired dependency can wake the case automatically; a serious integrity failure stops later writes until targeted checks confirm recovery.

A failure can stop changes without stopping evaluation.

The worker can continue examining cases and recording what it would have done while leaving them unchanged. A failed readback, broken case boundary, duplicate-effect risk, data-safety breach, or severe quality pattern stops later writes immediately without erasing the evidence needed to diagnose the problem.

Recoverable failures restart only after targeted checks show that the failure is gone and the connected system again behaves as expected. A breach of the data boundary requires external security or platform approval before writes can resume.

Learning runs on a slower clock than the case.

Case clock

New case → investigate → decide → verify → execute → read back. In production, the worker will finish supported work without waiting for model improvement.

Learning clock

Completed outcomes → offline comparison → controlled release → monitoring → retain or reverse. New prompts, models, rules, and allowed actions must earn their place before changing live behavior.

In production, a separate observer will watch aggregate behavior, with special attention to false approvals, false changes, unresolved cases, lookup use, and shifts in the mix of work. It will be able to stop further changes when a severe pattern appears. It will not rewrite or reroute an individual case, so monitoring will not become a second hidden decision-maker.

The core worker is built and tested. Production impact is not yet proven.

The full path has been tested against the cases that distinguish a demo from an operating worker: concurrent change, duplicate execution, partial failure, ambiguous readback, rollback and reconciliation, dependency repair, zero-write continuation, serious write stops, and evidence-based restart. Changes to rules and approved actions are tested against the cases they affect before they can become active.

The remaining work is the live production connection: the exact fields and actions the connected system accepts, the credentials required to use them, and written approval to make changes. Until that connection is active, the tests establish the worker’s behavior, controlled execution, and audit history—not production accuracy or operational impact.

The result is not a model wrapped in warnings. It is an AI given a real job inside a system that proves its exact decision is supported before the machine acts—and confirms the result afterward.
