Engineering deep dive

The AI owns the judgment. The harness earns the right to act.

The engineering problem is not how to make a model sound certain. It is how to let an AI investigate a messy case, commit to a useful decision, and then prove that decision is safe enough for a machine to execute.

A QA answer is useful only when the operation can act on it.

A free-form explanation is not a QA decision. It does not say which field may change, what value the system expects to find, which evidence supports the replacement, or what must happen after the edit. It also cannot protect itself from stale data, a duplicate instruction, or a write that only partly succeeds.

The worker solves those problems by separating two forms of authority. The AI has authority to interpret evidence and make the QA judgment. The harness has authority to decide whether that judgment may cause a write.

The separation matters because each side is strong where the other is weak. The AI can connect context that ordinary rules cannot. Plain code can enforce boundaries that must never drift.

The complete case is the first control.

The model never begins from a warehouse row or a reviewer’s final answer. The worker assembles one current case containing only the facts needed to decide and execute QA: supplied and verified values, evidence, lifecycle state, rules, and the actions permitted for that product.

Historical reviewer outcomes may be used in offline evaluation, but they do not enter the live prompt. That prevents the model from copying the answer it is supposed to produce.

01

Claim the caseScope before intelligence

Take only supported case types and record the version being evaluated. Unsupported work remains in its ordinary source workflow.

02

Assemble the recordOne case, one truth surface

Gather current facts, evidence, allowed actions, and the exact handbook rules that apply.

03

InvestigateRead only, case bound, receipted

Let the AI retrieve an approved missing decision fact without exposing another case or an open-ended search surface.

04

DecideApprove or exact change

Require one structured business outcome with citations, rationale, and a complete action when a change is proposed.

05

VerifyRebuild what code can prove

Check evidence ownership, rule validity, source freshness, field authority, action authority, and whether the proposed value follows from the record.

06

ExecuteApply exactly once

Write only a verified decision through the narrow destination contract, using the expected current value to guard against concurrent change.

07

Read backThe destination is the final witness

Read the case again, compare the actual result with the approved decision, and record the proof needed to explain the outcome later.

The model may investigate, but it may not improvise authority.

A tool request names the missing fact, the reason it matters, and the current case. The tool either returns a case-bound fact with a receipt or refuses. The model cannot invent a new tool, request a write, broaden the case, or turn lookup exhaustion into approval.

The investigation budget expands only when a permitted lookup is still producing decision-relevant evidence. Exhaustion creates a non-actionable system state: no decision is silently converted into approval, and no write occurs.

The verifier does not decide the case a second time.

The AI handles equivalence, context, and interacting rules. The verifier handles hard truths that software can establish without interpretation. It asks whether the AI’s decision is internally coherent, supported, authorized, current, and safe.

Evidence

Does every cited fact exist in this case?

Invented receipts, cross-case references, and unsupported replacements stop the action.

Rules

Does the handbook basis exist and apply?

The AI cannot cite a rule that is absent, inactive, or outside the case’s product scope.

Freshness

Is the source still the version the AI read?

An expected current value prevents the worker from overwriting a newer human or machine change.

Authority

May this field and action be changed here?

The destination accepts only approved fields, value forms, and QA actions.

Isolation

Did every lookup and receipt stay inside one case?

Case identity travels through the full investigation and verification chain.

Safety

Would the write introduce forbidden or unsafe content?

Unapproved free text and sensitive material cannot cross the write boundary.

Execution has two valid outcomes: confirmed action or zero writes.

A verified decision is previewed against the current destination, applied once, and read back. The execution record includes the before value, intended change, destination response, and actual final state. Repeating the same instruction does not repeat the business effect.

Confirmed action

The destination matches the decision.

The case is approved or changed, the required QA action is complete, and the audit history preserves what was proposed, checked, written, and read back.

Zero writes

The system cannot prove a safe completion.

The case remains unchanged. Unrelated cases continue. A repaired dependency can wake the case automatically; a serious integrity failure stops later writes until recovery is proven.

Stopping writes does not stop observation.

The worker separates judgment from write authority. If a failed readback, broken isolation boundary, duplicate-effect risk, data-safety breach, or severe quality pattern appears, later writes stop immediately. The system may continue evaluating cases without changing them, which preserves evidence for diagnosis without increasing the impact.

Recoverable failures restart only after targeted checks show that the failure is gone and the destination again behaves as expected. A breach of the data boundary requires external security or platform authorization before write authority can return.

Learning runs on a slower clock than the case.

Case clock

New case → investigate → decide → verify → execute → read back. The worker completes supported work without waiting for model improvement.

Learning clock

Completed outcomes → offline comparison → controlled release → monitoring → retain or reverse. New prompts, models, rules, and allowed actions must earn their place before changing live behavior.

A separate observer watches aggregate behavior, with special attention to false approvals, false changes, unresolved cases, lookup use, and shifts in the mix of work. It may stop write authority when a severe pattern appears. It cannot rewrite or reroute an individual case, so monitoring never becomes a second hidden decision-maker.

The engineering is complete where the repository can prove it.

The full path has been tested against the cases that distinguish a demo from an operating worker: concurrent change, duplicate execution, partial failure, ambiguous readback, rollback and reconciliation, dependency repair, zero-write continuation, serious write stops, and evidence-based restart. Changes to rules and approved actions are tested against the cases they affect before they can become active.

The remaining boundary is external. Production activation still requires the exact destination contract, credentials, and written platform authorization. Until that connection is live, the implementation proves repository-owned behavior and containment—not production accuracy or operational impact.

The result is not a model wrapped in enough warnings to be tolerated. It is an AI given a real job inside a system that can prove what the AI saw, what it decided, what the machine changed, and whether the destination agrees.
